# Incident, 2026-07-28 — the L1 stopped finalising for ~14 hours

**Cause:** the L1's only validator ran out of P-Chain fee balance and was deactivated.
**Fix:** `avalanche validator increaseBalance`. One command, no restart, no redeploy.
**Prolonged by:** the watchdog, which read the node's error reply as "node down" and restarted a healthy cluster roughly every 15 minutes.

## What it looked like

Everything that touched the chain hung. Admin buttons sat at "Working…", the
wallet never confirmed, `scripts/unstick.js` reported nonces that would not
clear. The deployer had 28 transactions queued (mined 225, pending 253) and none
of them moved.

But the node was *not* down. It answered every request:

```
API call rejected because chain is not done bootstrapping
```

and its health endpoint said exactly what was wrong:

```
299jCTH4Erm…  not connected to enough stake: connected to 0.000000%; required at least 80.0000
bootstrapped  subnets not bootstrapped
```

## The actual cause

CSB is an ACP-77 L1. Its validators are registered on the Fuji **P-Chain**, and
each one pays a **continuous fee out of a balance held there**. When that balance
reaches zero the validator is *deactivated*: it stays listed in the validator
set and contributes no stake.

```bash
curl -s -X POST -H 'content-type:application/json' --data '{
  "jsonrpc":"2.0","id":1,"method":"platform.getCurrentValidators",
  "params":{"subnetID":"fgNiKVRTRJFZbCzSUPJMix6YdG2HfpXGf1LP9rQ58b5TU9mJL"}
}' http://127.0.0.1:9650/ext/bc/P
```

```json
{ "nodeID": "NodeID-BoRS383b4Z9ZdsJSVUcnrXNCXh5Qj93ux",
  "weight": "100",
  "validationID": "2rrjPnaiB3PnatWdkZH37yJqFHBePUupuC5cFPsLXXZja6EBrh",
  "balance": "0" }
```

`balance: "0"` — deactivated. With the L1's one validator inactive, connected
stake was 0%, the 80% threshold was unreachable, the chain never finished
bootstrapping, and it accepted transactions it could never finalise. That last
part is what made it look like a mempool problem: transactions were *accepted*,
so every tool reported a queue rather than a refusal.

The money was never missing. `csb-deployer` held **1.229 AVAX on the P-Chain**
the whole time. It had simply never been moved into the validator's fee balance.

## The fix

```bash
avalanche validator increaseBalance --fuji \
  --key csb-deployer \
  --validation-id 2rrjPnaiB3PnatWdkZH37yJqFHBePUupuC5cFPsLXXZja6EBrh \
  --balance 1
```

Recovery was immediate and required no restart — the P-Chain reactivates the
validator on its own. Height went 225 → 266 within minutes as the backlog
drained.

Verify:

```bash
avalanche validator getBalance --fuji --validation-id 2rrjPnaiB3PnatWdkZH37yJqFHBePUupuC5cFPsLXXZja6EBrh
curl -s http://127.0.0.1:9650/ext/health | python3 -c "import json,sys; print(json.load(sys.stdin)['checks']['299jCTH4ErmwFMB3ZKa18Ck9EDzc99DMD48zkszxcArpaUfTqW'].get('error','HEALTHY'))"
```

## Why it took so long to find

Two things sent the diagnosis the wrong way, and both are worth remembering.

**The watchdog turned a fixable fault into an unstable one.** Its `height()`
parsed `"result":"0x…"` out of the RPC reply. The bootstrapping error has no
`result` field, so `height()` returned empty — which the script treated as "the
RPC is not answering at all", its one restart-worthy condition. It stopped and
started a live node every 15 minutes for hours. Those are the
`shutting down node {"exitCode": 0}` lines in the node logs: clean, deliberate
shutdowns of a working process. They also destroyed the evidence, because each
restart reset the picture just as it was being read.

**Every symptom pointed downward, and the cause was sideways.** Process state,
disk, RAM, database, node version and log files were all examined and all fine.
Nothing on the machine was wrong. The empty thing was a balance on a *different
chain*. The one early clue — `disconnectedValidators: ["NodeID-1111…6DBWJs"]`,
the all-zeros placeholder — was read as a corrupted registration rather than as
"the active validator set is empty".

## What changed

- **`ops/csb-watchdog.sh` no longer restarts anything.** It checks validator
  balances first, distinguishes an error reply from an unreachable socket,
  reports failing health checks by name, and exits 1 for a human to read.
  Timer moved 5min → 15min.
- **Validator balance is now the monitored signal.** It falls visibly over days
  and no restart can ever help it, which makes it the opposite of every other
  check here: it warns *before* the outage instead of describing one.

## Standing risks

- **One validator.** CSB's L1 has exactly one registered validator
  (`NodeID-BoRS…`, weight 100). The other two nodes track the chain but do not
  validate. Any single-validator problem is a total outage. Adding validators is
  the real fix; the balance alert only buys warning time.
- **Top-ups are manual.** 1 AVAX at the observed burn rate lasts a while, but
  nothing renews it. Check `getBalance` periodically and keep Fuji AVAX on
  `csb-deployer`'s P-Chain address
  (`P-fuji1mwwasu75mmwehls89rych7mxrnu0936lc8fpwv`).
- **avalanchego 1.14.1 vs Fuji 1.15.0.** The nodes log
  `unknown network upgrade detected` with an activation time of 2026-07-28
  15:00. Peers are on 1.15.0. If a 1.14.1 node cannot follow the P-Chain after
  activation, the L1's validator set becomes unreadable and the chain goes down
  the same way. Unresolved at the time of writing; avalanche-cli is 1.9.6.
