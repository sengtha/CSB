🇰🇭 CSB Staking

unmodified Synthetix StakingRewards, in two configurations

What this is

The contract is Synthetix's StakingRewards, compiled from the genuine upstream source — the most-forked staking contract in DeFi, and the ancestor of nearly every "farm". Two pools run it against the same staking token and differ only in what they pay out: one rewards an ordinary ERC-20 with no compliance hooks, the other rewards KHRt.

This is the first experiment here whose reward is a separate asset from the gated one, and that changes what can go wrong. The two pools fail in opposite directions.

The staking token is an ordinary ERC-20 with no compliance hooks and no faucet here — the deployer holds the supply and has to send you some before any of this does anything.

Both plain tokens are Uniswap's test ERC-20, whose symbol happens to be UNI-V2. They are not LP tokens and have nothing to do with the pool on the Liquidity page — check the addresses above rather than the symbols.

Whoever holds a stake accrues a reward. Whether they can ever take it depends on which token the pool pays. Check any address against both pools.

What the experiment found

1. The ungated pool leaks the asset itself. The staking token has no compliance hooks, so an attested holder can simply hand some to an address with no attestation, which then stakes, earns, and collects. Every earlier experiment here leaked a claim whose redemption stayed blocked. This leaks spendable value — and it is then transferable onward to anyone, with no gate anywhere.
2. The gated pool manufactures a debt it can never pay. Rewards accrue to the unattested staker exactly as normal, and getReward() reverts, because paying means transferring KHRt. The protocol's books record an obligation to a party that cannot receive it. That is not a leak — it is a stranded liability, and the perimeter causes it rather than preventing it. The debt does not lapse; it keeps growing.
3. The refusal arrives unlabelled. Synthetix is built on OpenZeppelin 2.3.0, which predates custom errors: its SafeERC20 makes a low-level call and checks only whether it succeeded, discarding the revert data. So the failure surfaces as SafeERC20: low-level call failed and an operator or auditor gets no on-chain indication that identity was the cause.
4. The stake is not trapped, only the reward. withdraw() moves the staking token, which is ungated, so it succeeds. exit() also tries to collect, so it fails. The same position, two entry points, opposite outcomes — a front-end offering only "exit" would appear broken for this user while "withdraw" worked.

Worth stating plainly: a compliance perimeter placed under an unmodified protocol does not only fail to contain value. It can also create obligations that nobody can discharge.
